## Что реализовано

- `ultra_regress.cpp`: динамически уменьшенный вес требований пустоты; варианты начального веса 32/64/112/160; исправлен выход при недопустимом отдельном корне; квоты разнообразия по числу активных эмиттеров.
- `ultra_core.cpp`: предвычисленные маски достижимости на 1–4 такта с учётом активности, геометрический градиент к недостающим клеткам. Маски половин комбинаций объединяются битовыми операциями в переборе 64×64. Поддержаны запросы продолжения из произвольной позы и фиксированного/свободного конца.
- `run_ultra.py`: динамический граф нормализованных поз принятия; точные в смысле симуляции рёбра с ровно одним принятием; DP по числу копий с выбором свободного терминального состояния. Вес ребра — длина лучшего найденного перехода, а не доказанный оптимум. Реализованы A→A, A→B→A и свободный A→B. Старое regenerate используется только как дополнительный кандидат для сравнения, а не как обязательная схема.
- Портфель разных весов, отражение и поворот геометрии с обратным преобразованием команд; кандидаты выбираются по полной длине. `candidates_focus` хранит отдельный короткий дополнительный поиск, без конкурирующей перезаписи основного набора.
- `assemble.py`: best-of-all merge по отдельным случаям, включая свежий baseline команды; проверка независимым solve_l5.verify; запуск неизменённого validate_l6_sandbox.cjs на отдельном объединённом наборе.

Готовые программы лежат в `final/level-6/answer_*.txt`. Для слияния команды используйте именно final, а не промежуточные candidates. Полная таблица по случаям: `case_results.csv`. Все прогоны с бюджетами, числом проверок и пиковой памятью: `benchmark*.jsonl`, плоская таблица `benchmark_flat.csv`.

## Проверка и измерения

- `prove_abstraction.cjs` создаёт две реальные истории из пустого поля, заканчивающиеся принятием с одинаковыми эмиттерами и различной материей вне target|forbid. На 120 одинаковых последующих тактах сравниваются релевантная материя и счётчики принятия. Оригинальный JS: PASS, 11 принятий в обеих историях. Результат: `abstraction_proof.json`.
- Все улучшенные программы независимо проверены Python; финальный объединённый набор целиком проверен оригинальным JS. Лог: `sandbox_validation.txt`, итог: `SUMMARY.json`.
- `ablation.json`: при одинаковом бюджете 600 мс и width=56 прежняя регрессия против UltraRegress на первой копии enormous: case 65 — лучшие 74 против 68; case 52 — прежний поиск не нашёл решение в трёх бюджетах, новый нашёл за 62 такта; case 115 — 80 против 56. Это сравнение коротких поисков, а не доказательство оптимальности.
- Измерено 949 прогонов по случаям и 15,074,575,447 проверок комбинаций; это не число уникальных состояний. Сумма измеренных длительностей поиска: 512.3 с. Пик рабочего набора C++-движка: 5.28 MiB; память Python-обёртки отдельно не измерялась.
- Дополнительные переходы графа дали накопленно 266 строк улучшения относительно маршрутов, доступных сразу после регрессии в тех же прогонах. Этот показатель относится к поисковым запускам, не является независимым разложением финальной экономии относительно свежего GitHub.

## Воспроизведение

Windows, MSVC x64, Python и Node; новых Python-зависимостей не требуется.

Из experiment_ultra:

```powershell
python -B ..\compile_helper.py ultra_regress.cpp
```

Из корня репозитория:

```powershell
node experiment_ultra/prove_abstraction.cjs
python -B experiment_ultra/run_ultra.py --pilot --ms 700 --width 40 --variants 0,1,2 --graph-budget 5
python -B experiment_ultra/assemble.py
node experiment_ultra/final/validate_l6_sandbox.cjs
```

Последнюю команду выполняйте с рабочей директорией experiment_ultra/final, поскольку валидатор использует собственное расположение для файлов (из корня также допустимо: node experiment_ultra/final/validate_l6_sandbox.cjs).

## Дальнейший резерв

Наибольший практический резерв: более сильные рёбра для плотных enormous (включая частично улучшенный case 129), увеличение разнообразия поз принятия и совместный выбор первой копии/продолжения. Для medium текущий портфель дал небольшой эффект; прежние многокопийные CP-циклы уже сильны. Min-plus и построение полного графа не нужны при K<=19. Не увеличивайте бюджет одинаково для всех случаев; используйте case_results.csv и профили неудач.
